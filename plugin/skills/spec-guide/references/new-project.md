# Begin from an idea

Converse in the user's language and work at their pace. Write the brief and later documents in the project's document language (see the CLI reference). First invite their own description. Reflect what they said, separate confirmed choices from hypotheses, and ask only the few missing questions that affect the next decision. Do not invent features to make the brief look complete.

Establish the intended experience, who it is for, target platform, smallest useful/playable scope and non-goals. Record unknowns with their impact. Choose an engine, framework or infrastructure when these needs justify it, rather than treating the template's tools as mandatory.

For a game, clarify the core player action, rules and state transitions, the round/progression structure and success/failure or other goals, if they apply. Distinguish essential mechanics from later presentation. Randomness, time and input should have controllable boundaries for fast rule tests. Ask about multiplayer, persistence and other major scope decisions only when relevant; do not assume them.

When writing project files is in scope, maintain a short brief using [the brief template](../assets/project-brief.md) or a suitable existing document. Keep the owner's accepted intent distinct from an agent's suggestions. Make a small change proposal only after the intended behavior is sufficiently clear.

When the experience has a visual side and its look is still open, offer the SPEC design starters as conversation material and follow [design](design.md) to shape the project's own identity. Do not let a starter decide the identity for the creator.

Create agent instructions, document mapping, architecture and command definitions as the project reaches those stages. Do not manufacture empty files to pass a checker. At the idea stage a missing mapping is expected and the mechanical checker is optional. A brief conversation can finish with the captured vision and the nearest useful open decision; it need not start implementation.
