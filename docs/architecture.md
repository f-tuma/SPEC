# Go runtime and agent workflow

SPEC has one application service in internal/spec. The JSON CLI and the Charm TUI call that service. The TUI never maintains a second implementation of setup, update or rollback. Its model handles terminal events, previews and asynchronous operation results. Agents start through spec run rather than from the dashboard; an external document editor hands the terminal over and then returns to the TUI. After status, the TUI lists the release source's tags in the background without prompts and offers an update only when a newer stable release exists.

The terminal dashboard renders explicit human reports from service results; it never prints raw JSON. A left sidebar holds a menu of the actions that can currently run; the content column shows the status, or a plan, result or setup options. Narrow terminals use one column. Key handling and the Bubbles help bar share one set of key bindings. Mutating actions show a readable plan before confirmation. Status refresh and document discovery run asynchronously, including after partial failures. Recorded setup, document discovery, native installation and verified skill invocation remain distinct. DESIGN.md owns the interaction and typography rules.

The TUI reads and edits project documents through the service's ReadDocument and WriteDocument: paths stay inside the project and outside .spec, saves are atomic, keep the file mode and are refused when the file changed since it was read. Markdown is rendered with Glamour using a SPEC style without bold, italic or non-ASCII glyphs. The editor is the Bubbles textarea with nano keys or a small vim normal-mode layer; it refuses content the textarea would not keep unchanged. A per-user preference in the user configuration directory selects the key style or an external $VISUAL/$EDITOR.

Design starters are DESIGN.md files inside the plugin's spec-guide assets, read by the JSON CLI and the agent skill. Creating DESIGN.md from a starter writes only an absent file; choosing and personalizing a design is an agent conversation guided by the skill, not a dashboard feature.

The Go binary embeds all:plugin so compatibility manifests in dot directories are included. Versioned resources are extracted into .spec/marketplace/versions inside the selected project. The manifest version, file inventory and source commit identify an installed plugin. The CLI version is independent of that installed version.

Installation state retains schema 1 so the Go manager can read Python 0.2 installations. Resource hashes are checked directly; a legacy aggregate digest is not silently reinterpreted as a new digest algorithm. A new Go release obtains its own fingerprint and may retain the old release in rollback history. Git source discovery supports plugin/ and the old spec_cli/plugin/ layout.

Project setup preflights legacy OpenSpec and cache placement before managed writes. A per-project exclusive lock prevents concurrent managed mutations; an interrupted/crashed process can leave a lock that must be inspected before removal. Catalogs and the installation receipt are preflighted and staged together, with backup restoration on commit errors. Status detects a catalog that disagrees with the receipt, including drift left by a crashed process. Confirmation checks its baseline and rollback target before mutation. Skipped native refresh is marked stale; unknown legacy client versions remain unknown. Claude Code installs the plugin from the project catalog with project scope. Codex has no project scope, so its skills are copied into .agents/skills with per-file hashes recorded in the receipt (additive to schema 1); a copy counts as SPEC's when it holds the recorded content or the file of any installed release, which also covers an interrupted refresh. Refresh checks every target before it writes and stops at content SPEC did not write; uninstall deletes only copies with known content and lists the rest. A user file with exactly a release's content is therefore treated as SPEC's. Status reads Codex's configuration, following a symlink, only to name a global plugin an earlier version registered and the commands that remove it. Uninstall reads the receipt under the project lock, runs the client removals first and moves .spec aside and deletes it only when all of them succeeded. Temporary downloads are checksum-verified before execution. OpenSpec init runs in an isolated staging directory, and only absent integration files are copied. Existing config.yaml/config.yml and their planning shape are preserved. The document language is an additive receipt field; a new config also requests it in its OpenSpec context, while an existing config is only read to report the language it requests. The review procedure is another additive receipt field. For EGM, each client's own CLI installs the egm plugin from Google's repository at a pinned tag (Claude Code with project scope, Codex user-wide); SPEC reads the clients' records first, reuses a plugin or marketplace that is already there, refuses an egm marketplace from another repository and records only what it added (`extensions` in the receipt). Switching back or uninstalling removes only the Claude Code project plugin SPEC added; the shared marketplace and Codex plugin stay and are named with their removal commands. Codex's configuration is parsed as TOML; a file that cannot be read or parsed leaves EGM setup pending rather than assumed. Status reports the project checks recorded in .spec-pilot.json and never runs them. A SPEC binary older than these fields drops them when it rewrites the receipt; run setup again with the current binary afterwards.

Plugin updates are not CLI self-updates, OpenSpec upgrades, Git branch changes or product deployments. They reject modified managed resources. Native registration can remain pending and never proves skill invocation. Status and mechanical guard commands do not execute commands from project metadata.

The guard checks a bounded candidate map and explicitly mapped input files. Evidence is an unauthenticated path/hash receipt. Semantic correctness, omitted dependencies, UI behavior, external integrations and release acceptance remain separate assessments.

The release workflow tests the source on three runner operating systems before publishing six CGO-disabled binaries and archive checksums. A failing or unstarted runner blocks release. Cross-compilation alone does not establish native execution or native agent compatibility.

The root install.sh/install.ps1 bootstrap a prebuilt release. They never invoke Go or set up a product project. HTTPS supports public releases, authenticated GitHub CLI supports private assets, and an offline directory supports release files downloaded beforehand. Checksum and executable-version checks precede changes to the destination; staged replacement and a local lock preserve existing files on failure. The installer retains the executable and license notices without changing PATH or shell profiles. Source-build wrappers are separate in scripts/install-from-source.*. Native installer integration tests are configured on all three CI operating systems.
